# fx_sim — 仮想100万円 FX（主要JPYクロス）自動運用シミュレーション

実際の値動き（yfinance / JPY建て日足）を使い、**架空の100万円**で自動売買を検証する。
実売買・送金は一切行わない。投資助言でもない。

[crypto_sim](https://github.com/men0tai0ko/crypto_sim) の設計をFX
（USD/JPY・EUR/JPY・GBP/JPY・AUD/JPY）に応用したもの。データ取得・執行モデル・
戦略・レジーム判定・バックテスト・自動テスト・パラメータ感度に加えて、
`live_trade.py`（リアルタイム運用）・`dashboard.py`（ブラウザ表示）・
GitHub Actions（自動実行）も crypto_sim と同じ設計で用意している。

**運用状況（ダッシュボード）: https://men0tai0ko.github.io/fx_sim/**
（GitHub Actionsの初回実行後に有効になる）
GitHub Actionsが平日30分ごとに自動売買し、この画面に反映する。表示専用で、
この画面自体は売買には一切関与しない。

リポジトリ: https://github.com/men0tai0ko/fx_sim （公開）

## crypto_sim からの主な変更点

暗号資産とFXでは前提が違う部分があり、そのままコードを転用すると
静かに間違った結果になる。変更した箇所とその理由:

| 項目 | crypto_sim（暗号資産） | fx_sim（FX） | 理由 |
|---|---|---|---|
| ユニバース | BTC/ETH/XRP/SOL の4銘柄 | USD/EUR/GBP/AUD の対JPY4ペア | 「上昇銘柄比率」という指標を成立させるには複数銘柄が要る（USD/JPY単体では母数1で意味を成さない） |
| 年間の観測本数 | 365（年中無休） | 261（実測。土日休場） | `metrics.py` のボラ・Sharpe年率換算に使う定数。混同すると約1.18倍過大に出る |
| 日足欠損の判定 | 抜け＝すべて異常 | 平日の抜けだけ異常、土日は正常 | FXは土日休場が前提。`data.find_gaps()` を参照 |
| コスト前提 | 手数料0.15%+スリッページ0.10% | スプレッド相当0.01%（FEE=0） | 国内FX会社の多くは別建て手数料が無くスプレッドのみ。暗号資産よりコストは1桁以上軽い（要検証・概算） |
| レジームのボラ閾値(HIGH_VOL) | 90%（年率） | 15%（初期値） | FXは暗号資産よりボラが1桁小さい（USD/JPY 30日年率ボラ実測: 中央値9.2%・90%点14.5%）。90%のままだと常に「落ち着いている」判定になり指標が機能しない |
| レバレッジ・証拠金・スワップ | 該当なし（現物のみ） | 未対応（現物のみのまま） | FXの本来の姿（レバレッジ・スワップ）を省略した簡略版。「既知の限界」参照 |

`TREND_MA`（200日線）・`BREADTH_MIN`（50%）・`ATR_MULT`（3倍）・`MAX_WEIGHT`（30%）・
`COOLDOWN_DAYS`（10日）は crypto_sim の値をひとまず出発点として使っている
**未検証の初期値**。下記「パラメータ感度」の節を参照。

## 前提条件

- **ユニバース**: USD/JPY・EUR/JPY・GBP/JPY・AUD/JPY（JPY建て直接なので為替換算不要）
- **時間軸**: 日足
- **コスト**: スプレッド相当0.01%（要検証・概算。上表参照）
- **現物のみ**（レバレッジ・証拠金・スワップなし）
- **執行**: i日目の**終値まで**を見て決めた注文を、**i+1日目の始値**で約定
  （look-ahead bias 対策。crypto_sim と同じ）

## GitHub Actions で自動実行する

`.github/workflows/trade.yml` が平日30分ごとに `live_trade.py --ci` を実行する。
crypto_sim の trade.yml と機構は同一で、違うのはcronの曜日指定だけ
（FXは土日休場なので `1-5`＝月〜金のみ動かす）。

### 手順

1. Settings → Actions → General → Workflow permissions を
   **Read and write permissions** にする（状態の書き戻しに必要）
2. Actions タブでワークフローを有効化する（初回は手動実行で確認できる）
3. 画面を見たい場合は Settings → Pages で **Branch: data / (root)** を選ぶ
   （`https://<ユーザー名>.github.io/<リポジトリ名>/` で公開される）

### 仕組み

- 実行のたびに `data` ブランチから前回の状態を復元し、1回ぶん売買判断をして書き戻す
- `data` ブランチは毎回**1コミットだけの履歴に強制置換**する
- 静的ダッシュボード（`publish_static.py` が生成）も同じブランチに置かれる
- **両方（ローカルの `live_trade.py` とGitHub Actions）を同時に動かしてはいけない。**
  同じ状態を別々に更新して矛盾する

## リアルタイム仮想運用

過去検証とは別に、**いまの相場に対して架空の100万円を運用し続ける**常駐モードがある。

```bash
python live_trade.py            # 5分間隔で常駐（Ctrl+C で中断、状態は保存される）
python live_trade.py --once     # 1回だけ実行
python live_trade.py --status   # 現状だけ表示
python live_trade.py --reset    # 元手100万円から仕切り直す
```

`run_live.bat` をダブルクリックしても起動する。

1ループでやっていること・停止条件・二重起動防止・状態ファイルの1世代バックアップは
crypto_sim の `live_trade.py` と全く同じ（README「リアルタイム仮想運用」節参照）。
**FX固有の違いは1点だけ**: 土日は市場が休みで `fetch_live()` が空dictを返すため、
その間は「現在値を取得できませんでした（休場中の可能性）」として次ループへ回る
（想定内の挙動で、エラーにはしない）。

シャドー判定（実売買に一切影響しない記録専用の別パラメータ試算）は
`SHADOW_HIGH_VOL = 0.08` を使っている。これは前掲のパラメータ感度で見つかった
「0.08だけ他の値から浮いている」という境界事例を、日々の判定の一致率で
追跡するため（`results/shadow_regime.csv` に記録）。

| ドンチャン55/20 | -1.6% / -9.5% / -0.03 | +11.9% / -5.4% / 0.58 |
| 移動平均20/60 | +5.6% / -15.3% / 0.07 | +20.6% / -13.1% / 0.40 |

**crypto_sim とは違い、レジーム切替戦略が両期間ともベンチマーク（買い持ち・均等分散）に
Calmarで負けている。** これは想定内で、理由は上表の「初期値」節の通り、
HIGH_VOL をはじめとするパラメータがFXデータでまだ検証されていないため。
crypto_sim のレジーム切替が強かったのは、この作り込みを実際にやったからであり
（README「実運用戦略（レジーム切替）の検証」参照）、fx_sim はまだその手前の段階。

参考までに、単純なトレンドフォロー（ドンチャン20/10・移動平均5/25）は
2023-2026でCalmar 0.6台と悪くない。RSI逆張りは2018-2022で相対的に良く、
「暗号資産の強いトレンド相場では弱い」という crypto_sim の想定とは
様子が違う可能性がある（FXはレンジ相場の比率が暗号資産より高いため、と
考えられるが、これも今後の検証課題）。

### パラメータ感度（`python sensitivity.py`）

**追記: 当初「ボラ閾値(HIGH_VOL)は0.08〜0.25の範囲で結果が完全に同一」と
記録していたが、これは `regime.classify()` 側のバグが原因だった。**
`high_vol` をデフォルト引数（`= HIGH_VOL`）として受け取っていたため、
import時点の値がその場で固定され、`sensitivity.py` が
`regime_mod.HIGH_VOL` を書き換えて再検査しても反映されないまま検査が
走っていた（crypto_simで先に見つかった同じバグ。`classify()` を
`high_vol=None` 既定・呼び出し時に都度読み直す形に修正済み）。
以下は修正後に実データで再実行した結果（`* は現在の設定値`）:

| パラメータ | 値 | 2018-2022 Calmar | 2023-2026 Calmar |
|---|---|---:|---:|
| 大局トレンドの移動平均(日) | 100 / 150 / **200*** / 250 / 300 | -0.05 / 0.09 / **0.07** / 0.17 / 0.01 | 0.33 / 0.23 / **0.22** / 0.22 / 0.20 |
| ボラ閾値(HIGH_VOL) | 0.08 / 0.11 / **0.15*** / 0.19 / 0.25 | 0.02 / 0.05 / **0.07** / -0.03 / -0.03 | **0.69** / 0.18 / 0.22 / 0.22 / 0.22 |
| ATRストップ幅 | 2.0 / 2.5 / **3.0*** / 3.5 / 4.0 | -0.04 / -0.04 / **0.07** / 0.09 / 0.05 | 0.19 / 0.23 / **0.22** / 0.19 / 0.20 |
| 1銘柄上限 | 0.3* / 0.4 / 0.5 / 0.6 / 0.8 | **0.07** / 0.09 / 0.11 / 0.11 / 0.11 | **0.22** / 0.20 / 0.19 / 0.19 / 0.19 |

**新たに分かったこと（要フォローアップ、パラメータはまだ動かしていない）:**

- **ボラ閾値0.08で2023-2026のCalmarが0.69と、他の値（0.18〜0.22）から
  明確に浮いている。** 4値中3値が0.22近辺に固まっているのに対し
  最小値だけが3倍以上——サンプル数が少ないので偶然の可能性も排除できないが、
  境界（掃引範囲の端）での挙動なので、0.08よりさらに低い値も試して
  裾を確認する必要がある
- 崖検出（隣同士の急変化）自体は見つからなかったが、絶対水準は
  相変わらずベンチマーク（USD/JPY買い持ち0.28/0.43、均等分散0.09/0.62）を
  下回ったまま。**「上昇銘柄比率がJPYクロス4本では独立した情報を
  持っていないのでは」という当初の仮説は、まだ検証できていない**
  （HIGH_VOLの効きが確認できた以上、これは切り分けて調べ直す必要がある）
- 1銘柄上限が0.5以上で頭打ちになる傾向は、crypto_simと同じく再現された

過剰最適化を防ぐルールに従い、この結果だけを根拠にパラメータを
今すぐ変更することはしない。

## 既知の限界（今後の課題）

- **レバレッジ・証拠金・ロスカットを未実装。** 現物のみのモデルなので、
  実際のFX運用（多くはレバレッジあり）とは資金効率がまったく違う
- **スワップポイント（金利差調整）を未実装。** 特にAUD/JPY・GBP/JPYは
  無視できない額になりうる。ロング・ショートの持ち越しコストを反映していない
- **コスト前提が概算。** スプレッド0.01%は通貨ペア・時間帯・ブローカーで
  変わる実際の値ではなく、大まかな見積もり
- **レジームのパラメータが未検証。** crypto_simの値を出発点にしているだけで、
  上記の検証結果が示す通り、現状ではベンチマークに勝てていない。
  **そのため、この検証結果だけを根拠に実運用を開始した状態であり、
  勝てる保証があるわけではない**（架空資金のシミュレーションだからこそ、
  検証を続けながら並行して動かせるという位置づけ）

## 過剰最適化を防ぐためのルール（crypto_simと共通）

- 作り込みは 2018-2022 の期間だけで行う。2023- は検証にしか使わない
- パラメータを1つずらして崩れる結果は偶然とみなす
- コストを外した数字は見ない
- 取引回数が極端に多い戦略は、コストを上げて再確認する
